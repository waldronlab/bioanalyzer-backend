# Curator Desk CSV Format

This is the CSV contract between BioAnalyzer and the downstream curator
review tools (`curator_table/app.py`, a Streamlit dashboard, and
`curator_table_r`, a Quarto/R dashboard in the separate `curator-desk`
repo). BioAnalyzer produces this CSV; both review tools consume it. If
this column list changes, **both** downstream tools' `VALUE_COLUMNS`/
`ONTOLOGY_ID_COLUMNS` need to change with it - see the cautionary example
at the bottom.

Generated by `scripts/cli_rendering.py::_render_curator_desk_csv()`,
exercised by `tests/test_curator_desk_csv_format.py`. Produce it with:

```bash
BioAnalyzer analyze --file pmids.txt --format csv -o predictions.csv
```

`--format csv` **is** this schema — `curator_desk_csv` is accepted as an
identical alias (kept for scripts/docs that already reference it, e.g.
`scripts/curator_daily_pipeline.py`) but there is no separate, different
"plain csv" format anymore; the two names always produce the same output.
This was a deliberate simplification: an earlier version had `--format csv`
producing a different, older, Status-inclusive shape, which was a real
source of confusion (predictions.csv wouldn't match curator_table_r's
columns unless you remembered to type the longer `curator_desk_csv` name).

This is deliberately a **simplified, curator-facing** schema (per Levi
Waldron's review of the table): plain extracted values plus an ontology ID
per mapped field, no PRESENT/PARTIALLY_PRESENT/ABSENT Status or
Mapping-Confidence columns, no Priority score. If you need the fuller,
Status-inclusive export (e.g. for `scripts/eval/confusion_matrix_analysis.py`),
use `--format detailed_csv` instead - a separate, unchanged format covering
all 6 `ANALYSIS_FIELDS` including Taxa Level and per-field Status, not meant
for curator_table_r/curator_table.

## Encoding and structure

- UTF-8 encoded, standard `csv` module quoting (fields with commas/quotes/
  newlines are quoted automatically).
- One row per PMID. **Rows are deduplicated by PMID** - if the same PMID
  appears more than once in the input, only the first occurrence is kept.
- Always has a header row with exactly the column names below, in order.

## Columns

| Column | Type | Notes |
|---|---|---|
| `PMID` | string | Deduplication key |
| `Year` | string | Extracted via regex from `year` or `publication_date`; empty if neither yields a 4-digit year |
| `Title` | string | |
| `Journal` | string | |
| `Host Species` | string | Extracted value |
| `Host Species Ontology ID` | string | NCBITaxon ID, empty if unmapped |
| `Host Species Ontology Candidates` | string | `label\|ontology_id; label\|ontology_id` - up to 2 alternates, populated only when the mapping tier isn't `auto` (see `app/normalization/grounding.py`). Not meant to be read as a plain display column - consumed by `curator_table_r`'s mapping picker. |
| `Body Site` / `Body Site Ontology ID` / `Body Site Ontology Candidates` | | Same pattern, UBERON IDs |
| `Condition` / `Condition Ontology ID` / `Condition Ontology Candidates` | | Same pattern, EFO IDs |
| `Sample Size` | string | No ontology mapping - it's a number, not a term |
| `Sequencing Type` | string | No ontology mapping - BugSigDB's own controlled vocabulary, not an external ontology |
| `Differential Abundance` | string | `"Yes"` / `"No"` |
| `In bsgdb` | string | `"Yes"` / `"No"` - whether this PMID is already present in BugSigDB (`app/services/bugsigdb_check.py`) |

17 columns total (3 of which - the Ontology Candidates columns - are picker
metadata rather than visible table columns downstream).

## Mapping tiers (auto / review / none)

Each ontology-mapped field's `mapping_tier` (`app/normalization/grounding.py::tier_for`)
classifies how it was resolved: `auto` (matched via a static, curated lookup
table with full confidence - applied without curator review), `review`
(resolved via a live OLS/NCBI fallback, or an ambiguous multi-match - a
curator should confirm), or `none` (no ontology ID at all). Only `review`-tier
fields populate an `Ontology Candidates` string; `auto`-tier fields leave it
empty since there's nothing to review.

## Taxa Level and Status/Priority are intentionally excluded

BioAnalyzer extracts **6** fields end-to-end (Host Species, Body Site,
Condition, Sequencing Type, Sample Size, Taxa Level - see the root
`CLAUDE.md`); the LLM is no longer even asked for Taxa Level (removed from
`EXTRACTION_PROMPT`), since it's assigned by curators during manual curation,
not extracted from abstracts. Per-field PRESENT/PARTIALLY_PRESENT/ABSENT
Status, Mapping Confidence, and the derived Priority score are still computed
internally (status drives `mapping_tier`; both remain available via
`--format detailed_csv` for eval scripts) but are no longer part of this
curator-facing CSV. This is enforced by `tests/test_curator_desk_csv_format.py`.

## Downstream consumers must match this spec

Both `curator_table/app.py` and `curator_table_r/R/config.R` independently
define `VALUE_COLUMNS`/`ONTOLOGY_ID_COLUMNS` lists used for table rendering
and the curator feedback-form schema. Both must match the columns above
exactly (5 value fields, 3 of which also have an Ontology ID column) - not
6 value fields, since this CSV never produces a `Taxa Level` column.

**This has gone wrong before:** `curator_table_r/index.qmd`'s feedback-form
JavaScript once hardcoded a 6th `Taxa_Level_Status` field (and the repo's demo
`data/sample.csv` had a matching column) inconsistent with this spec and with
`R/config.R`'s own column list. The practical effect: the feedback form's
submission schema didn't match what `R/config.R`'s `feedback_schema()`
actually expected to read back. If you're changing this CSV's column list,
grep both downstream repos for `VALUE_COLUMNS`/`ONTOLOGY_ID_COLUMNS` before
you do.
